# 06 - Known Risks

- Agent drift: agents may infer features that were never approved. Mitigation: Jira + context bundle + stop-on-conflict rule.
- Cache source-of-truth confusion: the CGN-88 local Valkey candidate has append-only persistence for restart checks. Mitigation: keep it disposable, use it only for cache/rate-limit/ephemeral workloads, and never persist canonical identity or product state there.
- Contract drift: producer and consumer may evolve independently. Mitigation: shared contracts + contract tests.
- Memory drift: docs can become stale. Mitigation: memory check in PR/CI and required handoff update.
- Privacy drift: social/admin features may expose more than intended. Mitigation: server-side consent/block/RBAC and explicit safe projections.
- Scale assumptions: 5,000 registered users is not the same as 5,000 concurrent users. Mitigation: versioned capacity model, separate load profiles and explicit SLOs.
- Performance-target drift: initial 5K thresholds are engineering targets before real beta telemetry exists. Mitigation: keep them machine-readable, require Jira-reviewed changes, and never weaken thresholds only to make CI green.
- Premature infrastructure complexity: pipeline/infra can become the project. Mitigation: phase gates and local-first tools.
- Dependency vulnerability drift: a package can become vulnerable after merge even when code does not change. Mitigation: OSV + Trivy PR gates and scheduled weekly rescans.
- Container/base-image vulnerability drift: newly disclosed OS/library CVEs can affect previously clean images. Mitigation: Trivy image gate, scheduled rebuild/rescan and immutable SHA image promotion.
- Security-gate bypass pressure: teams may be tempted to weaken thresholds to unblock delivery. Mitigation: machine-readable fail-closed policy, Jira-reviewed exceptions, Sandeep review and expiry dates.
- SBOM provenance gap: generated SBOMs are CI artifacts but are not yet cryptographically signed/attached to registry artifacts. Mitigation: retain CycloneDX evidence now and add signing/attestation only in an explicitly approved supply-chain ticket.
- Local Terraform state: the zero-budget phase has no remote locking, shared state or managed backup. Mitigation: keep state uncommitted, limit this bootstrap to local environments, and require a separately reviewed backend migration before cloud/production provisioning.
- Cloud-scope drift: a future agent could accidentally add a managed provider/backend to the local bootstrap. Mitigation: Terraform contract tests and CI reject cloud provider/backend/resource declarations in the zero-budget root.
- Local-vs-managed Kubernetes gap: k3d/K3s can prove Kubernetes service discovery, ingress prerequisites and NetworkPolicy behavior, but not cloud IAM/load-balancer/storage semantics. Mitigation: keep app manifests Kubernetes-standard and require a separately reviewed managed-cluster migration ticket before production cloud use.
- Local ingress exposure drift: developer ports could accidentally become publicly reachable if bound to all interfaces. Mitigation: `cgn.local-network.v1` requires loopback-only API/ingress bindings and contract tests reject `0.0.0.0`.
- Local cluster dependency drift: k3d/K3s/kubectl versions can diverge across developer machines. Mitigation: pin CI versions, pin the K3s image in repository config, and document the supported local stack.
- Local PostgreSQL admin misuse: `cgn_admin` is a bootstrap superuser and can cross service boundaries. Mitigation: reserve it for initialization/migration/backup only, keep it environment-secret, and require service-specific runtime roles in owning service tickets.
- Local database topology gap: one Docker PostgreSQL process does not model managed HA, replicas, IAM or TLS. Mitigation: keep service connection settings environment-driven and require a separately reviewed managed-database migration before production cloud use.
- Local backup data exposure: developer dumps may contain sensitive data once product data exists. Mitigation: write local dumps only under ignored `.local/`, never upload them by default, and define encryption/retention in the future production backup ticket.
- Ownership drift: downstream services may duplicate another domain's source of truth or bypass APIs/events. Mitigation: `cgn.bounded-contexts.v1` plus contract tests and mandatory architecture review for ownership changes.
- Projection authorization drift: stale feed/story/notification/admin projections could expose content after block, deletion or consent changes. Mitigation: projections remain non-authoritative, must consume owning-domain policy/state changes, and may never grant access the source domain denies.
- Premature contract invention: freezing architecture can tempt agents to invent endpoint paths or event names before feature scope exists. Mitigation: CGN-32 freezes boundary rules only; detailed contracts require the owning Jira ticket.
- Monorepo coupling drift: services may start importing each other's implementation packages because source is nearby. Mitigation: `cgn.workspace-boundaries.v1` and `pnpm ci:boundaries` reject direct service-to-service/app-to-service workspace dependencies.
- Shared-package business leakage: a shared package can become a hidden source of domain truth. Mitigation: shared packages remain cross-cutting/contracts only and cannot depend on app/service implementations; business ownership remains defined by `cgn.bounded-contexts.v1`.
- GitHub Free private-repository governance gap: protected branch/ruleset enforcement is unavailable for the desired zero-budget setup. Mitigation: team policy forbids direct main pushes, Main CI audits that Sandeep performed main entry and that the SHA is associated with a PR, and production deployment remains a separate owner-only manual workflow. This is detection, not prevention.
- Delivery-smoke coverage gap: current E2E/k6 gates validate the deployment mechanism through health/readiness, not the future full product journeys or 5,000-user capacity. Mitigation: keep these gates green now, then add real Playwright journeys/service integration tests and CGN-284 load profiles as product code lands.
- Production-target gap: release and rollback workflows are dry-run validations because no approved real production host/registry/secrets target exists. Mitigation: never claim public deployment until hosting, persistent staging, backups, observability and immutable artifact promotion are connected and validated.
- Private GitOps repository access gap: the Argo CD ApplicationSet points to the private CGN repository, but CGN-92 intentionally does not commit a repository credential. Mitigation: local validation proves installation and object wiring only; persistent staging sync needs an approved runtime secret or GitHub App integration in a later ticket.
- GitOps drift: manual kubectl changes in a future persistent staging cluster could diverge from repository intent. Mitigation: Argo CD ApplicationSet self-heal/prune is configured for approved paths, while production promotion remains owner-controlled.
- GitOps blast-radius drift: an ApplicationSet can accidentally include app/service or workflow paths before those deployment contracts are ready. Mitigation: `cgn.staging-gitops.v1` whitelists `infra/k8s/base` only and contract tests reject broader source paths.
- Helm base-chart scope drift: a generic chart can silently absorb probe/autoscaling/IAM rules owned by later tickets. Mitigation: `cgn.helm-base.v1` and contract tests reject CGN-45/CGN-60/CGN-61 concerns in the CGN-44 base chart.
- Helm service-readiness gap: most service workspaces are package boundaries without runnable images yet. Mitigation: validate the reusable chart with health-demo now and require each owning service ticket to provide its image/value contract before deployment.
- Helm promotion drift: staging and production can accidentally reference different or mutable artifacts. Mitigation: `cgn.helm-promotion.v1`, exact SHA rendering, equality checks and owner approval.
- Production promotion target gap: CGN-93 proves production intent only because no real production cluster/registry credential is approved. Mitigation: keep promotion render-only until a separately reviewed production target exists.
- Migration blast-radius risk: a migration runner could target the wrong service database or execute arbitrary paths. Mitigation: service allowlisting from `cgn.postgres-databases.v1`, owner-role execution, repository-contained SQL paths and one-service-per-job policy.
- Migration rollback gap: a successful schema change may still be incompatible with a future application release. Mitigation: pre-migration backup and restore proof are mandatory now; service tickets must define backward-compatible expand/contract migrations before real production rollout.
- Probe endpoint drift: a service can enable shared probe defaults before it implements compatible health endpoints, causing rollout failures. Mitigation: generic probes default off, owning services opt in only after endpoint support, schema validation rejects invalid paths, and local Helm install smoke proves enabled health-demo behavior.
- Probe tuning drift: thresholds that are too aggressive can create restart storms or remove healthy pods. Mitigation: versioned `cgn.kubernetes-probes.v1` defaults, bounded schema ranges, Jira-reviewed changes and Kubernetes event/status observation.
- Autoscaling-capacity drift: arbitrary replica bounds can be mistaken for proof that a service supports the 5,000-user beta. Mitigation: HPA utilization targets come from `cgn.capacity.v1`, generic replica bounds stay unset, the 2–4 profile is smoke-only, and CGN-284 owns real load/soak calibration.
- Health-demo resource profile is only calibrated by a shortened 25 RPS smoke with a 100-VU pool configured, plus disposable CPU/memory pressure on an ephemeral runner. Do not reuse it as service-specific sizing or 5K capacity evidence; CGN-284 full load/soak and owning-service workloads remain required.
- PDB availability mismatch: a disruption budget can block maintenance or provide false resilience when replica count is too small. Mitigation: PDB is opt-in, validation pairs it with a multi-replica smoke profile, and service-specific production sizing requires evidence.

- Staging-recovery coverage gap: CGN-227's new green rollback rehearsal exercises a GitHub-hosted ephemeral Docker health-demo, not rollback of a live Argo CD/k3d cluster or persistent user data. Mitigation: require a separate explicit, reversible GitOps/Kubernetes rollout-and-rollback acceptance test before production deployment.
- Change-authority gap: private GitHub Free does not enforce the desired protected branch setting. Mitigation: Sandeep-controlled PR review, fail-closed checks and post-merge Main CI auditing; treat any direct push as a process violation requiring an incident investigation, not a successfully prevented action.
